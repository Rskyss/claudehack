# 开发规范

本规范依据 `vibe-workflow` 及其规划、施工、自测、台账和版本规则整理，结合 ClaudeHack 的本地网络与权限边界执行。目标是让用户能从仓库里查清楚：为什么改、改了什么、测过什么、还有什么没完成。

## 1. 工作顺序与文档权威

执行顺序：**读台账 → 核实需求和现状 → 确定范围 → 实施 → 自测 → 独立复查 → 台账登记 → 用户验收 → 授权发布**。

| 文件 | 负责回答的问题 |
| --- | --- |
| `AGENTS.md` | 新会话或新开发者从哪里开始、哪些底线不能跳过 |
| `docs/开发进度跟踪.md` | 当前进行到哪里，用户定过什么口径，还有哪些遗留 |
| `docs/<任务名>/需求共识.md` | 大任务要解决什么、明确不做什么、如何验收 |
| `docs/<任务名>/方案.md` | 如何实现、影响哪些部分、风险和技术约定 |
| `docs/<任务名>/任务清单.md` | 先后顺序、依赖和每步验收标准 |
| 任务验收记录 | 用什么证据支持完成结论 |

台账是唯一的开发状态总索引。外部流程的计划、spec 和施工日志作为辅助材料链接到台账；不能因使用另一套工具就省略登记。已批准的大任务文档落在上述固定位置，其他重复设计稿改成指针，避免多个权威版本。

## 2. 需求大小与授权

涉及钱或账、数据表结构、跨多个功能模块、预计超过半天，或用户明确表示尚未想清楚，按大任务处理。完成需求共识、方案和任务清单；方案和清单经用户确认后实施。包含多个协作模块、后台机制或外部服务的方案，应说明架构、数据流和统一机制。

小任务也要用易懂的话说明目标、影响范围与验收方式。能从代码、文档或现有授权查到的内容先查；真正影响用户体验、数据、费用或授权范围的歧义再请用户决定。用户已经明确授权的同一动作不反复确认；新增影响与原授权不同的动作单独确认。

用户委托技术选择时，记录所做选择及理由。口头委托实现不等于批准付款、批量处理历史数据或改写已发布 Git 历史。

## 3. 修复前必须回答的三个问题

1. **根因在哪一层？** 是配置加载、网关连接、PAC 分流、浏览器状态、系统权限还是外部平台？同类问题是否还出现在其他路径？
2. **现在是否必须改？** 已复现的正确性、安全性或一致性问题优先；没有证据、代价大于收益或不影响当前任务的事项记入取舍，不顺手重构。
3. **能否沿用既有机制？** 优先修正已有逻辑；不为单个症状增加另一套代理、状态源或长期后台服务。

外部 AI 或扫描器的判断先核实，不直接当结论。批量检查的判据需在已知正确与已知错误的样本上验证，避免把正确配置改坏。

修复代码后默认不重跑历史任务、不清洗旧账号或浏览器数据。确有必要时先列影响范围、费用及恢复方式，取得对应授权。

## 4. 本项目的修改边界

- 已经通的出口地址、端口、路由名单、浏览器配置和服务启动方式，除非是已确认问题的必要改动，否则保持不变。
- 改网关时先备份、在隔离副本中复现和验证；必要时使用临时回环端口做实际连接测试，通过后才替换运行文件。
- 重启只针对必要的服务，说明可能短暂重连；不为了测试关闭全部网络或重置用户浏览器。
- 不清除 Cookie、登录状态、钥匙串或账号资料来制造“干净环境”。需要处理时另行明确范围。
- 修改名单时核对 PAC、SOCKS 分流、扩展 host permissions、content-script matches 和请求头规则；同步核对豁免项及域名边界，不能误匹配相似域名。
- 平台 KYC、银行卡 3DS 与本地网络故障分开诊断。没有交易关联证据，不把出口混用断言为某次认证的唯一原因。

## 5. 实施与检查

功能和缺陷代码遵循：先写能反映问题的测试 → 观察预期失败 → 最小修改 → 观察通过 → 跑完整相关套件。测试外部依赖时在网络边界使用替身，不把模拟结果写成真实服务结果。

逐项施工并验证，不把多个未验证改动堆在一起。先检索已有实现；保留可解释、可回退的改动，避免额外依赖和重复机制。

文档、图片和现成配置资产采用与其性质匹配的检查：链接和锚点、格式语法、实际渲染、与源配置一致性。纯文字不写只检查原文存在的伪单元测试；复制现有钩子时用真实临时 Git 仓库验证正反样本。

每个任务先自审，再由未参与实现的审查者复查“有没有做漏、有没有做多、有没有实质错误”。有子代理能力时使用独立代理；没有时开展明确记录的独立检查。复查意见先核实，有效问题修正后重新复查。

同一问题连续失败两次时先停下重复尝试，第三次前改变方法；三次仍无法解决时报告已试方法、现有证据和具体阻碍。

## 6. 测试证据分层

| 改动 | 必须留下的验证证据 |
| --- | --- |
| 网关逻辑 | 正常连接、配置错误、重试边界、超时与异常清理的回归结果 |
| 分流名单 | 保护域名、子域、豁免、相似域名、IP 字面量与名单一致性 |
| 实际网络 | 使用了哪个入口、请求类型、是否符合预期出口；不公开真实凭据 |
| root 服务 | 所有者、文件和父目录权限、普通用户不可写、服务运行状态 |
| 浏览器变更 | 实际使用的配置文件、所走页面、观察结果和未覆盖范围 |
| README / 视觉 | 相对链接与锚点、代码块、图像实际显示；不把历史测试徽章当实时 CI |
| Git 发布规则 | 真实临时仓库中的允许与拒绝样本，以及钩子的已知限制 |

全量套件命令：

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v
node --check extension/shield.js
bash -n macos/proxy-guard.sh
sh -n .githooks/pre-push
git diff --check
```

测试命令成功只证明对应范围。用“测试内容 → 操作 → 观察到的结果”报告；失败、跳过或未覆盖必须写明。HTTP 403 不等于业务成功；本地 IP 检查不等于付款成功；自测通过不等于用户验收通过。

不为证明连通性擅自购买订阅或提交身份证件。真实付款与身份认证需要对应授权，由其实际结果决定该流程能否验收。

## 7. 敏感数据、权限与清理

- 真实 `residential.json`、密钥、密码、Cookie、账号、订单、完整运行日志、浏览器配置和带凭据的备份不进入 Git。
- 示例使用文档地址和明确占位符。凭据受文件权限保护不能写成“已加密”。
- 发布前检查待提交文件集合及内容；不要把整个运行目录或用户主目录初始化成仓库。
- root 执行的脚本和二进制必须在 root 管理、普通用户不可写的路径；同时检查父目录和软链接，不只检查文件的 0755。
- 测试用临时账号、数据和配置完成后清理。诊断所需备份和回归材料可以保留在受限本地目录，但说明保留用途，不能宣称全部已删除。
- 不为验证失败回退而让已登录请求经过未知出口。使用不含账号数据的探测或隔离测试。

## 8. 台账与验收

任务开始时登记 🔄；自测和复查通过后标为 ⏳；只有明确取得用户验收确认后才标 ✅，并记录日期和确认方式。

每条记录包含：需求、用户确定的口径、实现、自测证据、未覆盖范围、遗留、用户验收和发布状态。记录用产品语言，不只堆函数名。

历史补录必须注明补录，不伪造当时不存在的方案、批准或验收。“用户没反对”不是通过；允许上传代码也不自动代表付款等业务流程已验收。

## 9. 版本号规则

仓库版本与 Chrome 扩展 manifest 版本独立记录。仅改文档或仓库治理时，不为凑版本而调整扩展版本。

| 情况 | 版本变化 |
| --- | --- |
| 正式对外上线且质量条件全部满足 | 首次转为 `v1.0` |
| 用户获得新的可用能力 | 功能位加一、修复位归零，如 `v0.1.2 → v0.2` |
| 没有新增能力，仅修复、优化、加固或收尾 | 修复位加一，如 `v0.1 → v0.1.1` |

修复位为零时省略；修订号只用数字；不跳号、不倒退。本仓库从 `v0.1` 开始建立规范版本；此前两条提交作为迁移前历史保留。

发版通常对应台账中的顶层任务首次通过用户验收。同一任务追加的小修正默认并入后续版本，不单独发版，除非用户主动要求；分量是否足以独立成版拿不准时请用户决定。

到达 `v0.99` 时不直接续为 `v0.100`：先判断是否具备 `v1.0` 的质量条件；不具备则先补条件，不能为了继续编号而宣称正式上线。

`v1.0` 不是“仓库已公开”的同义词。需要核心链路有统计证据、失败提示可信、自动备份与恢复演练、故障可发现、能回滚、隐私承诺兑现；收费产品还需支付、退款、凭证和计费验收。本仓库尚无全部证据，不宣称已经满足。

## 10. 一个版本，一个主干提交

本地可小步提交便于回退；发布前把属于同一版本的代码、测试、文档、台账和验收记录收齐，形成一个主干提交。

标题使用 `vX.Y 一句话主题`，有修复号时为 `vX.Y.Z 一句话主题`。主题简短、让用户读懂变化。正文按下面三组记录；没有内容的组可省略：

```text
v0.1 本地代理工具与开发规范

新增功能：
- 提供本地代理、域名分流、浏览器扩展和 CLI 出口校验工具。

优化功能：
- 整理分步配置指南，并在仓库留下测试与开发进度记录。

修复bug：
- 修复配置错误回退、连接异常清理和特权执行路径问题。
```

不把非版本 `docs:`、`fix:`、`chore:` 提交推到主干；不发版的零碎改动留在本地，或经授权推临时分支做 CI。不能先发布再补一串台账、验收和 README 提交。

## 11. 推送拦截与最终检查

启用从工作流原件引入并在本项目加固的钩子：

```sh
git config core.hooksPath .githooks
```

每次 clone 或换机器后重新启用。钩子检查发往 `main` 的提交标题，要求数字形式的两段或三段版本及非空主题；提交范围无法读取时拒绝推送。其他分支和 tag 不受该标题检查约束。**它不验证用户授权、正文分组、版本递增、一个版本是否拆成多条提交，也不是服务器端分支保护。** 这些仍必须人工或由代理逐项检查。连接器和 API 写入同样适用，不能因为不触发本地 hook 就绕过。

引入原件时，真实临时 Git 历史测试复现了畸形版本号被放行和历史读取失败仍放行两项问题；项目钩子据此改为严格匹配并在读取失败时关闭通路。未修改用户全局 skill 原件。

发布前逐项确认：

- [ ] 必要检查通过，失败和未覆盖事项已公开记录。
- [ ] 独立复查结束，台账与验收记录完整，用户确认状态真实。
- [ ] 同一版本的全部材料收齐，版本号与正文一致。
- [ ] 待提交内容完成敏感信息检查，现有正常功能没有无关改动。
- [ ] 当前远端头已核对，没有覆盖他人或其他会话的新提交。
- [ ] 用户授权覆盖本次推送；tag、Release 和历史改写按对应动作确认。

推送后从远端复查提交和文件。没有创建 tag / Release 时明确写“未创建”，不把普通推送说成完整 Release。

## 12. 处理已经发布的不规范历史

发现旧历史不规范时先登记事实，准备目标版本和完整提交正文，并保留可恢复的旧头引用。**未经用户明确同意，不 squash 已公开提交、不强推、不重指 tag。**

若用户批准合并历史，先核对远端仍是确认过的旧头，再用带确切旧 SHA 的 `--force-with-lease`；若远端已变，停止覆盖并重新核对。禁止无条件 `--force`。

若用户选择保留旧历史，则把它们作为迁移前记录保留，从下一个规范版本开始执行；不假称已经把旧历史整理干净。
